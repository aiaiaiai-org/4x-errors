# Running the collector

## Configuration

Everything is read from the environment. Nothing is read from a file in the
repository, and nothing is compiled into the image.

| Variable | Required | Meaning |
|---|---|---|
| `DATABASE_URL` | yes | PostgreSQL connection URL. Server side only. TLS is forced for any non-local host. |
| `ERRORS_INGEST_TOKENS` | yes | JSON object of `project` → array of SHA-256 token digests |
| `DATABASE_MAX_CONNECTIONS` | no | connection pool size, default 8 |
| `PORT` | no | listen port, default 8080 |
| `WEB_CONCURRENCY` | no | Puma workers, default 2 |
| `PUMA_THREADS` | no | threads per worker, default 8 |
| `LOG_LEVEL` | no | default `info` |

## Local development

```sh
docker run --rm -d -e POSTGRES_HOST_AUTH_METHOD=trust -p 5432:5432 postgres:17
export DATABASE_URL=postgres://postgres@127.0.0.1:5432/4x_errors
export TEST_DATABASE_URL=postgres://postgres@127.0.0.1:5432/4x_errors_test

bundle install
bundle exec rake db:migrate
bundle exec rake ci          # formatting, lint, the whole test suite
bundle exec puma -C config/puma.rb
```

The test suite needs a real PostgreSQL. Examples tagged `:database` exercise
partial unique indexes, check constraints, an immutability trigger and a
recursive query; none of that is worth testing against a substitute.

## Migrations

```sh
bundle exec rake db:migrate      # apply everything pending
bundle exec rake db:current      # exit non-zero if anything is pending
VERSION=20260905000300 bundle exec rake db:rollback
VERSION=0 bundle exec rake db:rollback   # empty schema
```

Sequel's timestamp migrator is used, so migrations from separate branches
converge without renumbering.

### Rollback strategy

Every migration has a `down`, and `VERSION=0` returns the database to empty.
Two things are deliberately not reversible:

- **Browser role privileges are not restored.** `20260905000400` revokes all
  privileges from the Supabase `anon` and `authenticated` roles. Its `down`
  disables row level security again but does not re-grant anything: giving a
  browser role access to these tables is never a rollback step. Restore it by
  hand if it is ever genuinely wanted.
- **Data is not recoverable by rolling back.** `error_events` is append only;
  dropping the table drops the occurrences. Take a backup before rolling a
  migration back in production. Supabase's point-in-time recovery is the
  intended mechanism.

Forward fixes are preferred to rollbacks for anything that has already run in
production. Roll back only a migration whose branch was never merged.

## Ingest tokens

A token authenticates exactly one project. The pipeline then refuses any
payload claiming to belong to a different one, so a leaked token cannot be used
to write under another project's name.

```sh
bundle exec rake tokens:issue PROJECT=nilx-one/web
```

The task prints the token once and the digest to configure. Only the digest is
stored anywhere: the deployment environment never holds a usable credential,
and comparison is constant time.

```
ERRORS_INGEST_TOKENS={"nilx-one/web":["<digest>"],"nilx-one/ai":["<digest>"]}
```

**Rotation.** Configure both digests, hand the new token to the project, then
remove the old digest. Several live tokens per project are supported precisely
so rotation needs no downtime.

**Revocation.** Remove the digest and restart. There is no cached state.

## Production database validation

`.github/workflows/production-validation.yml` runs the live check. It uses the
`production` GitHub environment, which is the only place `DATABASE_URL` exists.

It applies pending migrations, verifies none remain, then runs
`rake smoke:production`, which:

1. checks connectivity;
2. checks the schema is current;
3. checks `GET /health` reports the database dependency;
4. ingests one identifiable smoke event through the real application;
5. reads it back;
6. sends it again and checks both resolve to one event;
7. checks a token from another project is refused with `403`;
8. checks `received_at` was generated by the collector and `observed_at` was
   kept as reported;
9. removes its own records, and the registry entries it created if nothing else
   refers to them.

It never resets the schema, never writes anything that does not name itself as
a smoke record, and never deploys. The credentials it authenticates with are
minted for the run and discarded with it. The check is exercised by
`spec/collector/production_smoke_spec.rb`, so the run against the real database
is not the first time that code has executed.

Put required reviewers on the `production` environment so that a person
approves every run that reads the secret.

## Deployment

There is none yet, by design. `github.deployment.automatic` is `false` in the
implementation contract and no workflow in this repository deploys anything.
When a runtime is chosen, it needs exactly two secrets — `DATABASE_URL` and
`ERRORS_INGEST_TOKENS` — and the image in `Dockerfile`.
